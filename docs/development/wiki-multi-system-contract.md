# Wiki multi-system development contract

Status: foundation for parallel development; not publication or deployment authorization.
Wiki baseline: `0115e131d2cb4c5a9306b5cb8e6de8d3ffc1de27`. Core source: `6a300933435c633b51f1d446fca09b9810dceb9e`.

## Identity, authority and navigation

The existing Site → Wiki → private Rules Core tunnel and named operation allowlist remain the only runtime reference transport. Core lists permitted descriptors and returns ruleset ID, fingerprint and native rule envelope. Use `api.openRulesetReader(rulesetId)` from app bootstrap: it discovers the exact authorized descriptor and returns a snapshot-pinned reader. No fallback to first-party for missing, denied, malformed or stale contexts. Core's private reference endpoints currently use the same foreign-catalog distribution policy as public reads (first-party authenticated exception only). A separate Core-authorized private preview policy would be required to read unpublished foreign catalogs at runtime without changing public publication. Fixture-driven renderer development needs no policy change. Do not modify policy or use public endpoints. The catalog navigation workstream must replace the temporary unavailable-route guard only when it can bind an authorized context and isolate all index, detail and history state.

`rules-context.js` is authoritative: context = { rulesetId, fingerprint, campaignId, campaignRevisionId }. Base ruleset identity is never campaign identity. Current readers reject any campaign; future authoritative campaign revision must come from Core, not Site roles, browser state or fabricated IDs. The descriptor and every read must match the exact ruleset and fingerprint. Fingerprint change requires re-discovery and a new context, not mixed pages.

Canonical paths (relative to hosted tool base): /rulesets/{rulesetId}, /rulesets/{rulesetId}/types/{kind}, /rulesets/{rulesetId}/rules/{ruleId}. Legacy first-party /rules/{id}, /references/{id}, category-family routes, /types/{kind}, /all and / remain supported. Explicit malformed/foreign qualified paths must not silently become first-party. Use ruleRoute/categoryRoute/catalogRoute for new links. Do not use a foreign entity ID in a legacy unqualified path. Preserve existing first-party links until navigation integration.

## Presentation interfaces

`native-presentation.js`: createRulesetReader(api, context) provides context, search(filters), resolve(ruleId), hrefForRule(ruleId). Resolve returns the exact Core envelope {rulesetId,fingerprint,rule:{id,name,kind,definition}}. Core definition is the full native record, including wrappers, not necessarily a uniform gameplay payload. Never mutate or flatten it in the common adapter. createPresentationInput(context,envelope,reader,{toolBasePath,renderSource,lifecycle}) supplies context, rule, record, source, sourcePackage, references, hrefForRule, renderSource and lifecycle. Source can be absent; do not invent attribution. The active dispatcher passes the optional app.renderNativeSource(input) hook through to the common presentation input. The hook returns a safe DOM node and may be supplied by the attribution workstream. A source hook supplies a safe DOM node; retain authored provenance and display catalog license when an authoritative source is available. Current private descriptor does not provide manifest attribution; catalog-level source disclosure may require a narrow Core contract before publication.

createNativeRendererRegistry(fallback) registers {id,supports(input),render(input),priority}. supports is a pure structural/capability predicate (kind alone is insufficient for incompatible schemas); equal-priority ambiguity is an error. render returns a detached DOM node or Promise of one. The shared generic fallback displays the complete record as inert text/DOM, including tables and nested values. It never executes inline tags, Markdown, HTML, or mechanics. Build richer structured-entry/tag rendering on renderStructuredContent; unknown shapes remain readable, not discarded. Explicit native ID references may be resolved via the context-bound reader; do not infer cross-catalog links from display names or 5etools tags. Existing native-rule-detail.js and resolved rule-renderers.js stay available; do not route foreign records through first-party specialized dispatch. Reconcile existing renderers by adapting input contracts, not duplicating layouts. The active native dispatcher uses the same registry for every native envelope. The first-party compatibility adapter has priority -1000 and preserves the current layout; structural adapters with ordinary priority supersede it. Unmatched foreign records use the shared generic fallback. New renderers return a detached node or array of nodes (or a Promise of either); the dispatcher supplies shared navigation chrome and mounts only current results. New renderers use renderNativeAttribution(input) or the same source hook in their own content. The legacy resolved-rule variation dispatcher remains intact; no unsupported campaign authoring is activated.

Registration ownership: native-renderer-registration.js is the composition root. Each independent workstream exports registerNativeRenderers(registry) in its preinstalled native-renderers-class.js, native-renderers-creature.js or native-renderers-reference.js slot. Register new modules there; do not edit native-rule-detail.js or app.js to add a renderer. Use unique namespaced IDs and structural predicates; coordinate overlapping predicates/priority. The active registry is app.nativeRendererRegistry. Direct fixture callers may instantiate createWikiNativeRendererRegistry().

The detail pane reads app.rulesContext when bound by catalog navigation, otherwise the first-party wikiIndex snapshot. Catalog navigation owns setting/replacing the immutable rulesContext from an authorized descriptor, supplying the unqualified native rule ID to renderRuleDetailPane, and canceling old detail reads before switching contexts. The pane resolves the requested record through the pinned reader when rulesContext is present; legacy first-party reads are also verified against the index fingerprint and requested ID. app.rulesContext must not be set to an unauthorized or guessed catalog. Existing foreign-route guard remains until navigation integration.

createRenderLifecycle() belongs to the owning surface; begin(context,ruleId) invalidates the previous lease and returns {key,signal,isCurrent}. Cancel on teardown, selection changes, catalog changes or navigation away. The live pane now cancels the preceding lease on selection and full app render; scope and empty-index transitions cancel it as well. The lease also checks the selection serial, bound context, index snapshot and mounted surface. Check isCurrent before every async success/error DOM commit; mountNativePresentation handles the top-level detached result. Nested async sections must also use the lease and check their own current mount; AbortSignal is advisory (existing private transport has no signal parameter). Retain existing render serial checks and explicit presentation hooks. No mutation observers.

## State

referenceKey(rulesetId,ruleId) is stable across revisions and suitable for identity/bookmarks/recent history. Any content cache, search cache, resolved reference cache or revision-sensitive reading position uses snapshotKey(context,...parts); readingKey(context,ruleId,view) includes the rule and view. Tuple serialization avoids delimiter collisions. Catalog fingerprint participates in cache and expansion state, not stable identity. Campaign identity and authoritative revision participate in snapshot keys; unrevisioned campaign state cannot enter reusable snapshot caches. Never reuse per-user access decisions or private record contents across sessions. First-party legacy storage remains unchanged while guarded; migrate legacy unqualified values only as first-party when explicitly reconciling state. Do not write foreign history into legacy unqualified stores. Do not persist campaign data or authoritative gameplay resolution.

## Fixtures and limitations

tools/fixtures/multi-system/manifest.json pins source files, IDs, systems, revision and manifest attribution. Files are verbatim record values reserialized without modification, not served from wwwroot. Fixture envelopes can be constructed with explicit synthetic test fingerprints; never represent these as runtime catalog fingerprints. The Tarrasque exercises a complex conventional legendary stat block. Current Core tree and the pre-rewrite first-parent tree at a66fcf904964440d766c0c49a799018c59945e1a contain no identified native multipart/Kaiju record; repository history searches for Kaiju, multipart and complex combatant returned no matches. The native monster-statblock foundation is approved design data, not a creature. Do not represent the Tarrasque as a Kaiju. The existing Wiki synthetic Kaiju regression record has been extracted to synthetic/kaiju-reference-fixture.json and is consumed by the original monster regression test. It is explicitly listed separately from the Core-native fixture entries, with pinned Wiki provenance, and is not assigned a native Core ID. A real authored multipart combatant fixture remains unavailable and requires Core content when approved; no fabricated rules were added to Core. The imported native files are heterogeneous; first-party loader may expand Origin traits. Fixtures are source records, not assertions of exact loader projections. No foreign publication, campaign authoring, browser selector, full specialized renderer reconciliation, or complete state migration is implemented here. Existing first-party legacy read paths remain active and foreign routes are explicitly unavailable in the current browser.

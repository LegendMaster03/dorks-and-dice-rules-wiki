## 2. Recovered lifecycle and limitations

**Implemented at the historical checkpoint.** A source-independent normalized RuleConcept with immutable anchor metadata could bind canonical entities. Global Rules Lawyer decisions were append-only: select-source, json-merge-patch, json-rule-patch, each pinned to an exact source revision, with actor/time/note and patch hash. Preview was stateless. Saved decisions were pending until deliberate publication. Global ruleset revision plus entries pinned decisions and sources; identical publication was idempotent. This was one global adjudicated Dorks & Dice baseline history, not evidence of multiple independently owned global/custom catalogs.

CampaignRulesetSelection was append-only and explicitly selected a published global revision. CampaignRuleDecision supported inherit-global, select-source, merge patch and structured patch. CampaignRulesetRevision and entries pinned selection, baseline entries, decisions and source revisions; publication was serializable, computed an effective-decision-set fingerprint, and returned existing latest revision if unchanged. See CampaignRulesService.cs at historical checkpoint, lines 14–57, 57–215, 215–320. Publication iterated baseline entries only. It did not implement a free-standing campaign-only entity addition: SetDecision required baseline concept membership. Additions of properties/array members within rules are not additions of whole native entities. A campaign can select a different source variation (replacement of implementation); there is no evidence in that model of independent native rule removal or full-record creation by campaign. Treat these as distinct extensions requiring scope approval, not resurrected features.

Baseline candidate discovery compared exact published global revisions. Preview reported added/removed/changed/unchanged concepts, decision kinds/numbers, and overrides remaining active, becoming inactive or becoming active again when a concept disappeared or returned. Initial preview treated all candidate concepts as added. Historical inactive decisions remained in history and did not count as pending when outside selected baseline. Selection and saving did not affect published campaign play. Inherit-global followed the pinned baseline; select-source replaced global patching; campaign patches replayed on resolved global rules, in deterministic order. Historical preview compared concept/decision metadata, not a full native semantic migration; CampaignRulesService.PublishAsync built entries from selected source IDs and did not in that loop revalidate every replayed patch. Native publication must validate the whole candidate before committing, including broken selectors/reference graphs.

**Source and adjudication:** raw source content immutable and package scoped; canonical entities and relationships were recognition metadata, not grants. Canonical revision/rename history permitted selection of a legitimate evolving concept (even category change); variant/reprint alone did not establish interchangeable identity. Resolved Wiki views could show accessible versions, provenance, effective category and deterministic unresolved fallback. Historical consumer reads also supported explicitly unresolved fallback for missing publication/entries; it was never a published decision or part of an immutable published entry set. Exact source update preview replayed stored patch, with explicit adopt/reject and separate publication; documentation describes optimistic decision/revision/fingerprint tokens and rejection scoped to exact pair. Later source-layer docs describe package-native content blobs, representations, entity revisions, canonical occurrences and explicit user_source_grant. Dev import/grant administration separate from Rules Lawyer; acquisition records do not grant access. Some source review documentation predates package-native changes; recover exact final schemas before porting. Wiki's retained adjudication queue calls discover, begin, reopen, clarification, escalation, defer and publication operations. These calls establish the retained UI surface; the final historical backend state machine and integration test evidence are recovered in section 11. Porting this implemented workflow is a separately bounded follow-on, not a prerequisite for campaign browsing.

**Authority:** the final historical RulesAuthority.cs required Dorks & Dice mode-scoped Rules Lawyer for global editing (legacy global fallback only when ScopedRoles is absent), explicit requested campaign membership in that mode for campaign read, DM for campaign mutation. Anonymous unauthorized, wrong-mode/nonmember campaign not found, player mutation forbidden. Rules Lawyer did not imply campaign authority, DM did not imply global authority; both independent of source grants. Final historical architecture names authorized DM/editor as design intent, but RulesAuthority.cs verifies DM only. Site's mode-scoped Editor is not a campaign editor permission. Site current domain has DM and Player grants; do not add an editor label or infer publication rights from one. Source administration required effective Dev, not Rules Lawyer; account self-grant and acquisition operations had separate semantics. Restricted contributors must be checked for effective rules, not just primary source; historical commits 747d3bd (contributor access) and b390456 (canonical equivalents) document this concern.

## 4. Native architecture reconciliation

Core NativeCatalogRegistry currently freezes configured ruleset IDs and maps each to independent NativeCatalogStore; TryGetStore does not fall back. NativeCatalogStore atomically holds one validated snapshot or unavailable reason; no I/O, archive, or reload. NativeCatalogLoader loads native/ only, validates identity/references and builds NativeCatalogSnapshot. A manifest and its fingerprint describe one package's current operative contents, not a database revision history. NativeReferenceEndpoints maps GET /api/private/rulesets, /{rulesetId}/rules and /{rulesetId}/rules/{ruleId}; descriptor is id, count, fingerprint, read=true/write=false. Search/detail return rulesetId/fingerprint and exact record envelope. No historical revision parameter, membership-aware scope, source grant, mutation, or effective campaign contract.

Recommended (pending approval): preserve registered base package stores; introduce Core-owned durable revision repository and native composition coordinator that resolves an exact base revision and approved decisions into one validated NativeCatalogSnapshot using the same native record/validation/index/search/resolve infrastructure. Refactor loader's common record validation/building if necessary; do not add a parallel source-resolution engine, write per-campaign files into Git/deployment native/ trees, or place every campaign in the static registry. Base registry remains authoritative for configured current packages; a revision selector/provider retrieves authorized historical and composed snapshots on demand. Use atomic publication and scoped caching with bounded lifetime and authorization rechecks. A loaded base can be archived once and referenced by many campaigns. Missing historical snapshot must fail explicitly, not substitute current catalog, first-party or an unapproved source. Independent package failures remain isolated.

Distinguish:
1. **Base system/package**: existing authoritative published native package (first-party-001, dnd-5e, dnd-5-5e, fate-condensed), stable package ID plus versioned content. It may be loaded privately without being eligible for any particular user or publication.
2. **Independent custom ruleset**: proposed separately identified owned package, native records and immutable publications; optionally derived from an eligible base. Do not presume global Rules Lawyer is its owner or that all campaign DMs can publish it globally. User ownership and permitted sharing are established design direction; exact access-grant and publication contracts need approval.
3. **Campaign draft modifications**: append-only selection/decision state tied to the Site campaign; baseline may be an eligible official or custom published revision, never implicit first-party. Preserve independent selected vs active pointers.
4. **Published effective campaign**: immutable Core publication scoped to campaign, derived from exact base revision and approved decisions, not a global catalog. Core-issued revision ID and effective fingerprint; no public distribution by virtue of campaign publish.

### Proposed durable model (logical requirements, not approved schema)

- Base/custom revision record: stable rulesetId, immutable revision ID/sequence, manifest/source provenance, exact native content fingerprint, content-addressed immutable artifact/record references, actor/time and parent/lineage where applicable. Native base fingerprint alone is not a published campaign revision or a sufficient guarantee of retrievability.
- Custom ruleset ownership/access and declared system/engine compatibility metadata; exact base link if derived; unique package-local IDs and scoped sequence. No custom ownership schema before approval.
- Campaign baseline selection: campaignId, selectionId/sequence, target rulesetId + base revisionId + fingerprint, actor/time, reviewed migration reference. Pending baseline and active revision pointers separate.
- Decision: immutable decisionId/sequence, scope, target qualified native identity and expected record revision/hash, kind, native patch/replacement payload, provenance/contributors, actor/time, note, migration disposition. Preserve inherit/reset. Candidate whole-entity add/replace/suppress operations need owner-approved semantics; do not silently overload JSON patch null to delete a whole rule. Campaign-only additions need their own persistent local identity and reference namespace, not a mandatory baseline entry.
- Publication: campaignRevisionId, campaignId, exact selection, exact decision set, effective record references and fingerprints, provenance/license dependencies, actor/time, immutable content or reproducible pinned artifact. Effective fingerprint distinct from base fingerprint; publication idempotency and revision identity separately defined. Same content may occur in different campaigns and revisions; no global access inference from shared hash.
- Transactional latest published pointer, concurrency/version tokens, referential integrity, append-only audit; preserve prior publication if composition, persistence, or authorization fails. Decide retention/migration of old DB with owner; never assume historic storage survived rewrite. Reuse content-addressed storage for deduplication but not for entitlement inference.

### Composition, references and execution

Key identity by package ID + native entity ID; add exact revision when comparing or resolving content. For campaign additions, reserve explicit scope-owned identity strategy before implementation; no collision with inherited native IDs or with another campaign's additions. Persist source identity, exact origin/revision/hash and explicit mapping separately from effective identity. Use explicit native references and validate all in effective scope. Replacing an entity must retain or explicitly migrate identity/reference contracts, not allow arbitrary cross-system raw source documents. Do not mutate original catalog or source. Reuse deterministic object/array patch behavior, then validate native schema, reference graph, wrappers, mechanical invariants and supported system capabilities. Revalidate every carried decision on baseline change. No automatic fallback to working/reference trees.

Native mechanics currently include snapshot-dependent engines and representative RulesetResolutionEndpoints that selects registered package + fingerprint and dispatches RulesetResolution.Evaluate(snapshot.RulesetId, request.Resolution), with complete=false. Custom/campaign ID is not necessarily a mechanics dispatch key. Separate system/engine compatibility from package and scope identity; engines must explicitly support effective content and revision before consumers use it. A valid displayed rule/patch is not proof an engine executes it. Do not route campaign mechanics to current base silently. Initial restoration may deliver published reference reads with explicit unsupported mechanics; Character Sheet/Block Initiative migration is separate acceptance.

## 5. Baseline migration behavior

Same ruleset revisions: reuse old added/removed/changed/unchanged diff and pending/active distinction. Compare stable qualified native IDs within known lineage, exact record hashes and schema/semantic changes; retain override history and classify remains active, inactive, candidate reactivation, incompatible patch, missing dependencies or explicit migration required. Reapply strict patches and validate full candidate. Reactivation for a genuinely restored same-lineage entity is reviewable; no automatic activation from a coincidentally reused ID. Preserve historical publication even when latest base unavailable. Preview identifies source restriction and unavailable entries without leaking them; mutation needs exact reviewed token and fresh authorization.

Between editions (e.g. dnd-5e to dnd-5-5e): reuse comparison UI, selection and publication lifecycle, not automatic same-ID matching. Require reviewed cross-edition correspondence and conversion of override semantics, category/reference and mechanics compatibility. Any candidate unmatched or ambiguous override remains inactive/unresolved until explicit disposition. Selecting another eligible edition never implicitly carries decisions by string equality.

Between systems (e.g. Fate and D&D): treat as a new system baseline with explicit reset/carry/conversion review. Do not translate ability scores, skills, actions, dice, character state or rule IDs by similarity. Preserve old decisions and published history. Allow a reviewed baseline switch only when unresolved active changes and dependent consumer migration policy are addressed; require explicit owner decision on whether an incompatible campaign may publish reference-only and how active character/encounter state is handled. No cross-system converter is in minimum scope.
